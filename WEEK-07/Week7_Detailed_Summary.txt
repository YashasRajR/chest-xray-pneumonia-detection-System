During week seven, my primary objective shifted from building new software features to aggressively testing and hardening the backend server we had already created. Because this is a medical application meant to diagnose pneumonia, it is absolutely critical that the system is stable and does not crash when deployed in a real hospital environment. To ensure this level of stability, I spent the week engaging in a process known as destructive testing. Instead of testing the system by uploading perfectly formatted X-ray images, I actively tried to break the Flask API by acting like a malicious user or a confused doctor who might upload the wrong files by mistake. This required a completely different mindset, focusing on finding the weakest links in the software architecture.

One of the first major vulnerabilities I discovered was related to how the server handled file uploads. I took a standard, multi-page PDF text document, manually changed the name of the file on my computer so that it ended with a dot jpg extension instead of a dot pdf, and tried to upload it. Because the server only looked at the name of the file, it assumed it was a valid image and tried to feed the text document into the deep learning model. This completely confused the image processing library, causing the entire backend server to instantly crash and shut down. To solve this, I had to completely rewrite the file upload logic. I implemented strict MIME-type validation, which means the server no longer trusts the name of the file. Instead, it reads the actual raw bytes inside the file to definitively prove it is a real image before doing any processing. Now, if someone uploads a fake image, the server safely intercepts it and gracefully rejects it. Instead of crashing, it simply returns a standard HTTP 415 Unsupported Media Type error, which translates to a polite warning message on the user's screen.

I also spent a significant amount of time testing the limits of the server's memory. I wanted to see what would happen if a user uploaded an exceptionally large file. I injected massive twenty-megabyte image files directly into the API. Because the deep learning model requires a lot of computing power to analyze images, forcing it to process such a massive file caused the server to freeze and consume almost all of the computer's available memory. This is known as memory exhaustion, and if it happened in a real deployment, it could bring down the entire application. By identifying this flaw, I was able to build safeguards into the code that analyze the file size the millisecond it reaches the server, automatically blocking anything that is too large and ensuring the server remains fast, responsive, and completely crash-proof.
