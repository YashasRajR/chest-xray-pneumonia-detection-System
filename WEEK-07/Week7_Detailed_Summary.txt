During the seventh week of my internship, my entire focus shifted from building new features to actively trying to break what we had already built. At this point in the project, the pneumonia detection website was fully functional when I used it exactly how it was meant to be used. However, I knew that in the real world, medical professionals are incredibly busy and might make mistakes. They click the wrong buttons, upload the wrong files, or sometimes bad actors even try to break the system on purpose. My goal for this week was to make the software indestructible, or at least as tough as possible. This phase is what software engineers call destructive testing or adversarial testing, and it completely changed how I looked at my own code.

I started by attacking the file upload system on the medical dashboard. I spent days just uploading the absolute wrong things to our server to see how it would react. For example, I took a normal PDF text document, manually renamed the file on my computer so it ended with dot jpg instead of dot pdf, and uploaded it to the server. At first, the server completely crashed. It tried to read a text document as if it were a picture, which completely confused the deep learning model and caused the entire backend application to shut down. To fix this, I had to dive incredibly deep into the backend Python code. I rewrote a large portion of the upload logic so that the server actually looks inside the file's raw binary data to confirm it is a real image. Now, it ignores the name of the file entirely and only trusts the actual internal contents. If someone tries to upload a fake image, the server safely rejects it and shows a polite error message on the screen instead of crashing the entire system. 

Next, I tested what would happen if I uploaded a massive file. I found an ultra high-resolution image that was twenty megabytes in size and uploaded it. The server struggled to process it, the website froze for almost a minute, and the computer almost ran out of memory. This was a huge red flag because if multiple doctors tried to upload large files at the same time, the entire hospital server could crash. I went back and added strict file size limits on both the webpage itself and the background server. I set the limit to exactly five megabytes, ensuring that anything larger was instantly blocked before it could even reach the deep learning model.

Finally, since the pneumonia detection logic was bulletproof, I focused heavily on testing the frontend User Interface on different devices and browsers. I purposely shrunk the browser window to the size of a mobile phone and a tablet to see if the buttons, text, and images would overlap or break. I noticed that the upload box became too squeezed on small screens. I spent the remainder of the week tweaking the CSS code, adjusting the margins, and writing custom layout rules to guarantee the dashboard remained perfectly usable and readable. Whether the doctor was using a giant desktop monitor in an office or a small tablet while walking around the hospital, the layout shifted dynamically to look perfect. It was incredibly satisfying to turn a fragile prototype into a robust, professional-grade medical application.
