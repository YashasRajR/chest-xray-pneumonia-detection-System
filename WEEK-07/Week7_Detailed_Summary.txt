During the seventh week of my internship, my primary objective shifted entirely from building new software features to aggressively testing and hardening the backend server we had already created. Because this is a medical application meant to diagnose pneumonia from chest X-rays, it is absolutely critical that the system is stable and does not crash when deployed in a real hospital environment. To ensure this high level of stability, I spent the entire week engaging in a rigorous software engineering process known as destructive testing. Instead of testing the system by uploading perfectly formatted X-ray images, I actively tried to break the Flask backend API by acting like a malicious user or a confused doctor who might upload the wrong files by mistake. This required a completely different engineering mindset, focusing on finding the weakest technical links in the software architecture.

One of the first major vulnerabilities I discovered was related to how the server handled incoming file uploads over the network. I took a standard, multi-page PDF text document, manually changed the name of the file on my computer so that it ended with a dot jpg image extension instead of a dot pdf, and tried to upload it. Because the server initially only looked at the name of the file to determine what it was, it assumed it was receiving a valid medical image and tried to feed the text document directly into the deep learning model. This completely confused the image processing library, causing a fatal error that made the entire backend server instantly crash and shut down. To solve this critical flaw, I had to completely rewrite the file upload logic at the routing layer. I implemented strict MIME-type validation, which means the server no longer blindly trusts the name of the file. Instead, it intercepts the upload and reads the actual raw binary bytes inside the file header to definitively prove it is a real image before doing any processing. Now, if someone uploads a fake image, the server safely intercepts it and gracefully rejects it. Instead of crashing, it simply returns a standard HTTP 415 Unsupported Media Type error to the frontend, which translates to a polite warning message on the user's screen.

I also spent a significant amount of time testing the limits of the server's memory allocation. I wanted to see what would happen if a user uploaded an exceptionally large file to the API. I purposefully injected massive twenty-megabyte image files directly into the system. Because the deep learning model requires an immense amount of computing power and RAM to analyze images and convert them into mathematical tensors, forcing it to process such a massive file caused the server to freeze and consume almost all of the computer's available memory. This is a severe condition known as memory exhaustion, and if it happened in a real hospital deployment with multiple users, it could bring down the entire local network. By identifying this architectural flaw, I was able to build safeguards deep into the Flask code that analyze the payload file size the millisecond it reaches the server. The code automatically blocks anything that is too large, ensuring the server remains fast, responsive, and completely crash-proof regardless of what the user attempts to upload.
